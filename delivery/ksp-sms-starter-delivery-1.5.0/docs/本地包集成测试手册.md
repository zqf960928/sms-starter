1. starter 能被业务工程通过 Maven 依赖正常引用
2. Spring Boot 启动时能自动识别 `SMS{...}` 配置并解密

## 2.1 职责边界

本 starter 的默认职责边界如下：

- starter 负责：从 SMS 获取凭据、在快过期时执行 `renew / reapply`、回读最新凭据、把最新值刷新到 Spring `Environment`
- 业务工程负责：决定何时切换新老凭据、如何平滑更新连接池、旧连接保留多久、切换失败后的回退与告警

也就是说：

- starter 是“最新凭据提供者”
- 业务系统是“连接池切换控制者”

不建议客户默认理解为“只要引入 starter，连接池就会自动无感热切换”。  
如果客户希望运行期无感切换，应由业务侧基于 starter 提供的最新值，自行实现连接池刷新器。

`1.5.0` 版本仍然保留 starter 直接更新 `DataSource / Hikari` 的能力，但这属于可选项，不作为默认推荐交付边界。默认建议保持 `datasourceEnabled=false`、`hikariEnabled=false`，由业务系统自己控制连接池切换。

另外，`1.5.0` 默认采用脱敏日志口径，不输出凭据明文、密文、签名串、请求体和响应体。

## 7. Demo 工程关键配置

配置文件位置：

- `E:\traecn\javasmsadpter\src\main\resources\application.yml`

当前已经配置了：

```yaml
spring:
  datasource:
    url: jdbc:mysql://192.168.0.130:3307/test?...
    username: SMS{mysql-sh:username}
    password: SMS{mysql-sh:password}

ksp:
  sms:
    url: https://192.168.0.130:8390
    domain: 1
    appKey: admin
    appSecret: 9d0022b3e66c87b066890baba1d481954a8b9c5ad3fa12de04596600c7acb5da
    version: "2"
    refresh:
      enabled: true
      lifecycleDriven: true
      datasourceEnabled: false
      hikariEnabled: false
      renewTtlSeconds: 3600
```

当前语义是：

- 启动时从 SMS 获取 `mysql-sh` 的密文
- 自动提取 `username`、`password`
- 运行期启用刷新线程
- 刷新逻辑使用 lifecycle-driven 模式
- starter 不直接接管业务连接池切换
- Demo 额外提供了一份“业务连接池管理器”，用于演示业务如何消费 starter 的最新凭据
- Demo 默认开启“业务自动检测凭据变化”示例逻辑，用于演示客户可参考的实现方式

### 7.1 关键配置字段说明

当前 Demo 中这段配置位于：

- [application.yml:L20-L42](file:///e:/traecn/javasmsadpter/src/main/resources/application.yml#L20-L42)

```yaml
ksp:
  sms:
    url: ${KSP_SMS_URL:https://192.168.0.130:8390}
    domain: ${KSP_SMS_DOMAIN:1}
    appKey: ${KSP_SMS_APP_KEY:admin}
    appSecret: ${KSP_SMS_APP_SECRET:******}
    version: ${KSP_SMS_VERSION:2}
    enabled: true
    cipherPrefix: SMS{
    jsonKey: value
    refresh:
      enabled: true
      intervalSeconds: 10
      leadTimeSeconds: 300
      refreshStatic: true
      datasourceEnabled: false
      hikariEnabled: false
      validateOnRotate: false
      validationQuery: "SELECT 1"
      evictDelayMs: 0
      lifecycleDriven: true
      renewTtlSeconds: ${KSP_SMS_RENEW_TTL:300}
      maxRenewFailures: 2
```

字段含义如下：

- `url`：SMS 服务地址
- `domain`：SMS 域 ID
- `appKey / appSecret`：starter 登录 SMS 的凭据
- `version`：SMS 接口版本
- `enabled`：是否启用 starter
- `cipherPrefix`：密文占位前缀，默认 `SMS{`
- `jsonKey`：当写成 `SMS{label}` 时默认取出的 JSON 字段
- `refresh.enabled`：是否启用运行期刷新线程
- `refresh.intervalSeconds`：刷新线程轮询间隔，单位秒
- `refresh.leadTimeSeconds`：旧版提前刷新参数；在非生命周期驱动路径中作为兜底
- `refresh.refreshStatic`：是否允许静态凭据进入刷新流程
- `refresh.datasourceEnabled`：是否由 starter 直接更新 `DataSource`
- `refresh.hikariEnabled`：是否由 starter 直接更新 Hikari 连接池
- `refresh.validateOnRotate`：切换后是否立即做连接校验
- `refresh.validationQuery`：连接校验 SQL
- `refresh.evictDelayMs`：旧连接驱逐延迟，`0` 表示立即驱逐
- `refresh.lifecycleDriven`：是否按平台返回的生命周期字段判断 `renew / reapply`
- `refresh.renewTtlSeconds`：每次续约请求的 `renew_ttl`，建议与平台实例 `ttl` 保持一致
- `refresh.maxRenewFailures`：连续续约失败达到阈值后转 `reapply`

对当前 Demo 而言，这组配置表达的是：

- starter 启动后会登录 SMS，并解析 `SMS{mysql-sh:username}` / `SMS{mysql-sh:password}`
- starter 会每 `10s` 检查一次动态凭据状态
- starter 自己负责 `renew / reapply / refetch`
- starter 不直接切业务连接池，因为 `datasourceEnabled=false`、`hikariEnabled=false`
- 业务侧通过 Demo 中的自动检测示例，自己决定何时把最新凭据应用到连接池

### 10.9 业务监测变化的参考逻辑

客户业务侧如果希望自动消费 starter 提供的最新凭据，可以参考 Demo 中的实现：

- 参考代码：[DemoBusinessDataSourceManager.java:L63-L95](file:///e:/traecn/javasmsadpter/src/main/java/com/example/javasmsadpter/DemoBusinessDataSourceManager.java#L63-L95)
- 连接池重建逻辑：[DemoBusinessDataSourceManager.java:L41-L61](file:///e:/traecn/javasmsadpter/src/main/java/com/example/javasmsadpter/DemoBusinessDataSourceManager.java#L41-L61)
- 变化判断逻辑：[DemoBusinessDataSourceManager.java:L213-L215](file:///e:/traecn/javasmsadpter/src/main/java/com/example/javasmsadpter/DemoBusinessDataSourceManager.java#L213-L215)

推荐实现步骤：

1. 业务启动后先初始化自己的连接池
2. 定时从 Spring `Environment` 读取 starter 刷新后的最新 `username/password`
3. 对比业务当前已应用的 `username/password`
4. 如果没有变化，则保持现有连接池继续服务
5. 如果检测到变化，则按业务自己的策略重建新连接池
6. 新连接池可用后替换旧连接池，再关闭旧连接池
7. 记录最近一次观察时间、最近一次同步时间、同步结果，便于排障

可以参考下面这段伪代码：

```java
@Scheduled(fixedDelayString = "${app.demo.businessRefresh.intervalMs:5000}")
public void autoRefreshIfNeeded() {
    if (!enabled) {
        return;
    }

    String latestUser = environment.getProperty("spring.datasource.username");
    String latestPass = environment.getProperty("spring.datasource.password");

    if (same(appliedUser, latestUser) && same(appliedPass, latestPass)) {
        return;
    }

    DataSource next = buildDataSource(latestUser, latestPass);
    testConnection(next);

    DataSource previous = currentDataSource;
    currentDataSource = next;
    appliedUser = latestUser;
    appliedPass = latestPass;

    closeQuietly(previous);
}
```

这个示例表达的核心原则是：

- starter 负责刷新“最新值”
- 业务负责判断“是否应用”
- 业务负责控制“何时切池”

如果客户需要更严格的平滑策略，还可以在这个基础上增加：

- 延迟关闭旧连接池
- 连接池切换失败回退
- 同步失败告警
- 多实例灰度切换

看启动日志和 `/demo/config`，确认：

- starter 已加载
- `SMS{...}` 已被正常替换为明文配置

### 11.2 运行期能力

- refresh manager 在运行
- 已拿到 `mysql-sh` 的生命周期信息

### 11.3 续约/重新申请能力

如果当前环境 TTL 较短、或者你愿意等待到窗口附近，再观察：

- 是否触发 proactive renew
- renew 失败后是否 fallback 到 reapply
- reapply 后是否重新 fetch cipher
- 本地生命周期缓存是否被刷新

### 11.4 客户需要自行完成什么

这个点建议在交付时明确写给客户：

1. 客户项目需要引入 starter 依赖并配置 `ksp.sms.*`
2. 客户项目需要把明文账号密码改成 `SMS{label:username}`、`SMS{label:password}`
3. 客户项目如果要运行期无感切换，必须自行实现“业务连接池刷新逻辑”
4. starter 不直接决定新老凭据切换时机，切换策略由业务系统自己掌控

## 13. 常见问题排查

### 13.1 Maven 找不到 starter 依赖

现象：

- `Could not find artifact com.ad:ksp-sms-spring-boot-starter:1.5.0`

处理：

1. 重新在 `E:\traecn\ksp-sms` 执行 `mvn clean install`
2. 检查本地仓库目录是否存在 `1.5.0`
3. 再回到 Demo 工程执行 `mvn clean package`

### 13.2 应用能启动，但配置没有被替换

现象：

- `/demo/config` 里还是原始 `SMS{...}` 语义或为空

处理：

1. 检查 starter 是否真的被引入
2. 检查 `application.yml` 中的 label 是否存在
3. 检查 `appKey / appSecret / domain / version` 是否正确
4. 检查网络是否能访问 SMS

### 13.3 启动时报登录或取密失败

处理：

1. 先检查 `url`
2. 再检查 `appKey / appSecret`
3. 再检查该用户是否有 `mysql-sh` 的权限
4. 如是证书问题，再看是否需要放开 TLS 校验

### 13.4 刷新线程没起来

检查：

- `ksp.sms.refresh.enabled=true`
- `/demo/refresh/status` 中 `beanPresent`、`running`

### 13.5 一直看不到 renew/reapply

这是常见情况，不一定是错。

原因通常是：

- 当前凭据还没进入主动窗口
- 服务端 TTL 比较长
- 当前实例暂时不需要 renew/reapply

这时候先确认：

- 刷新线程是否正常
- 生命周期字段是否已经取到
- cache 是否已更新
